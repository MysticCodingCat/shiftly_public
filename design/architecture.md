# 架構說明

## 整體流程

```
使用者在前端編輯設定 ──► Schema v1（JSON）
                              │
                    POST /api/solve（背景工作）
                              │
            ┌─────────────────▼─────────────────┐
            │ 1. 預處理                          │ 日期、週期、班別時間、上期班表、選擇器解析
            │ 2. 算術預檢                        │ 人數根本不夠 → 毫秒內回報缺多少人日
            │ 3. 建模                            │ 基本變數 + 需求 + 預班 + 各約束積木
            │ 4. CP-SAT 求解                     │ 多執行緒、時限由伺服器夾住
            │ 5a. 可行 → 軟違規回報、每人統計     │
            │ 5b. 無解 → 衝突診斷                 │ 逐一停用單一條件試解
            └─────────────────┬─────────────────┘
                              │
                 前端輪詢 /api/jobs/{id} 取得結果
```

排班引擎（上圖方框內）未公開，本 repo 只有其介面：資料模型 `backend/engine/schema.py`
與 API 層 `backend/api/main.py` 如何呼叫它。

## 資料模型（Schema v1）

一份設定檔完整描述一個排班問題，前端編輯的就是這份 JSON，引擎只吃它：

| 區塊 | 內容 |
|---|---|
| `horizon` | 排班期間，支援月曆月、四週、八週週期 |
| `calendar` | 國定假日、週起算日、變形工時區塊 |
| `shifts` | 班別與假別統一建模（`kind`: work / rest / leave），含起訖時間與工時 |
| `employees` | 年資、技能、可上班別、標籤 |
| `history` | 上期最後幾天的班表，供跨月規則使用 |
| `preAssignments` | 預班、預休、請假、禁排 |
| `demands` | 每日各班最低人數，可附資格條件（例如至少一名資深） |
| `constraints` | 約束積木實例：`block` 種類、`params`、`enforcement`（hard / soft）、`weight`、適用範圍 |
| `solver` | 時限、執行緒數、診斷設定（伺服器端一律再夾上限） |

「每人每日恰選一個班別（含休假）」是整個模型的基礎：決策變數是
`x[員工, 日期, 班別]` 的布林值，每個 (員工, 日期) 恰好一個為真。
休假也是一種班別，所以「休息天數」「例假」這類規則和工作班用同一套變數表達。

## 約束積木

每種積木是一個函式：讀取 `params` 與適用範圍，對模型加上約束或懲罰項。
硬性積木直接加約束；軟性積木加上鬆弛變數並以權重計入目標函數，
求解後再把每個鬆弛值翻譯成「誰、哪天、為什麼」的違規說明。

幾個代表性的建模手法（精簡可執行版見 `engine-excerpt/toy_scheduler.py`）：

- **滑動視窗**：「任意 7 天至少休 1 天」與「最多連上 6 天」本質相同，共用同一個實作；
  視窗跨到上個月時，已知的上期休假直接計入，沒有資料的天數悲觀視為上班
- **由資料推導規則**：兩班間隔下限不要求使用者列出禁止的組合，
  而是由班別起訖時間算出哪些「前一天 A 班、隔天 B 班」間隔不足
- **公平性**：以極差（max − min）而非變異數作為公平度量，維持線性、求解快
- **變形工時跨月**：四週區塊跨到下個月時，依落在本期的比例折算目標工時

## 無解時怎麼辦

1. **算術預檢**：先檢查「總需求人日」是否超過「可用人日」，這類問題不需要動用求解器
2. **衝突診斷**：逐一停用每條硬性規則與需求，各給短時限試解；
   停用後可行的，就是造成衝突的條件，直接建議使用者放寬哪一條
3. 診斷有總時間上限，避免規則很多時診斷本身跑太久

## 檢核器：第二份獨立實作

檢核器不建模、不求解，直接逐條檢查一份具體班表。它有兩個用途：

- 手動微調時毫秒級回饋（改一格就重新檢核）
- 檢核人工排的班表：單位不必改變作業方式，就能先看到現行班表的合規風險

檢核器和建模器對同一條規則各寫一次。測試要求所有模板的求解結果都通過檢核、零違規，
任一邊理解錯規則都會被抓到。

## 後端服務

- **FastAPI**：求解是 CPU 密集且耗時數十秒，所以以背景執行緒執行，前端輪詢進度；
  同時最多兩個求解，每個帳號同時一個
- **SQLite（WAL 模式）**：帳號、session、班表文件、求解紀錄；
  單機部署、備份就是一個檔案，線上備份用 SQLite backup API 取一致性快照
- **重啟容錯**：記憶體中的工作在重啟後消失，改由資料庫紀錄判斷工作是否被中斷
